# 数据库与索引（微信云开发）

> 这份文档写给两个人看：**维护云函数的你** 和 **写小程序前端的他**。
> 里面所有字段名都是**契约**，前端与云函数按同一份字段表读写，改字段必须两边一起改。

---

## 一、集合（Collection）

建**三个**集合，名字必须**一模一样**（区分大小写）：

| 集合名 | 用途 | 权限 | 大致条数 |
|---|---|---|---|
| `tasks` | 全部任务：日程 / 截止 / 子任务 | **仅创建者可读写** | 每人几十 ~ 几百条 |
| `settings` | 每人一条设置（开学日期、作息表、AI Key、提醒开关与额度） | **仅创建者可读写** | 每人 **1** 条 |
| `reminders` | DDL 到期提醒的记账（已提醒过 / 下发失败原因） | **仅创建者可读写** | 每人随提醒次数增长 |

⚠️ **三个集合的权限都必须设成「仅创建者可读写」**（设置步骤见第三节）。
默认的「所有用户可读，仅创建者可写」会让**任何人**都能读到**所有人**的日程 —— 这是这类小程序最容易出的隐私事故。

> **`reminders` 不建会怎样**：`remind` 云函数报 `collection not exists`，
> 表现为「到期提醒功能打开就报错」。不用提醒功能的话可以先不建。
>
> **为什么 `reminders` 也是「仅创建者可读写」**：它记着你的任务标题与截止时刻，
> 和 `tasks` 一样属于私人数据。它默认是**新建集合的默认权限**，很容易被漏掉。
>
> 三个集合的权限设置可以一次做完：`tasks` → `settings` → `reminders` 逐个点第三节第 4 步。

## 二、`tasks` 集合字段表

一条任务就是一条记录。**云数据库会自动给每条记录加 `_id` 和 `_openid` 两个字段**，
其余字段全部由 `cloudfunctions/tasks/lib/normalize.js` 归一化后写入。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 自动 | 云数据库主键，前端拿它做 `update` / `remove` |
| `_openid` | string | 自动 | **数据归属**，由云数据库写入；用户身份只认这个字段 |
| `title` | string | ✅ | 任务名，最长 100 字，**空标题会被拒** |
| `type` | string | ✅ | `'event'` 日程 / `'ddl'` 截止 / `'subtask'` 子任务；非法值退回 `'event'` |
| `date` | string | ✅ | `'YYYY-MM-DD'`；缺省补「今天」，格式非法会被拒 |
| `start_time` | string | | `'HH:MM'`；**没填就是空字符串 `''`**（不瞎猜时间）。`type='ddl'` 时恒为 `''` |
| `end_time` | string | | `'HH:MM'`；对 `ddl` 来说这是**唯一的截止时刻**，空串表示「当天结束前截止」 |
| `priority` | string | ✅ | `'high'` / `'mid'` / `'low'`；非法值退回 `'mid'` |
| `done` | boolean | ✅ | 是否手动勾选完成 |
| `parent_id` | string \| null | | 父任务的 `_id`（子任务用）；无父任务为 `null` |
| `repeat` | string | ✅ | `'none'` 不重复 / `'weekly'` 每周重复（课程） |
| `week_start` | number \| null | | 起始周次（1~30）；`repeat='none'` 时为 `null` |
| `week_end` | number \| null | | 结束周次；`repeat='none'` 时为 `null`。**`stats` 用它判断"已结课"** |
| `week_parity` | string | ✅ | `'all'` 每周 / `'odd'` 单周 / `'even'` 双周 |
| `periods` | string | | 节次范围，如 `'7-9'`（数组 `[7,9]` 会被拼成这个字符串）；无则 `''` |
| `location` | string | | 上课/活动地点，最长 60 字 |
| `estimate_min` | number | ✅ | 预计耗时（**分钟**）；`0` 表示"没估"，负数/字符串/缺失一律归 `0` |
| `created_at` | string | ✅ | 创建时间，北京时间 ISO 串（如 `2026-10-11T15:20:00+08:00`） |
| `updated_at` | string | ✅ | 最后修改时间，每次 `add` / `update` 都会刷新 |

### 字段约束小结（前端口径）

* `title` 是**唯一**必填项；`date` 不传就补今天。
* `type='ddl'` 时**不要传 `start_time`**：DDL 只有一个截止时刻，云端会把它挪进 `end_time` 并把 `start_time` 清空。
* `repeat='weekly'` 才需要 `week_start` / `week_end` / `week_parity`，其他情况云端会把周次存成 `null`。
* `update` 只认**白名单字段**（就是上表除 `_id` / `_openid` / `created_at` / `updated_at` 之外的全部业务字段）；
  传 `_openid`、`_id`、`created_at` 会被**丢弃**并在返回值的 `rejected` 里列出。

## 三、权限设置步骤（控制台点一遍）

1. 打开 [微信开发者工具] → 顶部菜单 **云开发** → 进入 **云开发控制台**。
2. 左侧选 **数据库**。
3. 如果还没有集合：点 **`+`** 新建集合，分别建 `tasks`、`settings`、`reminders`
   （名字区分大小写，**不要**写成 `Tasks`）。
4. 选中 `tasks` 集合 → 点右上角 **权限** 标签（有的版本叫「权限设置」）→ 选 **仅创建者可读写** → **保存**。
5. 对 `settings` 与 `reminders` **各重复第 4 步**（**三个都要**，漏一个就是一处隐私口子）。
6. 验证：权限页面上应该显示「仅创建者可读写」。可以再到「数据」标签里手工加一条记录试试 ——
   用小程序端读别人的数据会返回空，这才是对的。

> **为什么云函数还要自己带 `_openid` 条件？**
> 云函数用的是**管理端权限**，会**绕过**上面这条权限规则。也就是说：
> 权限设置保护的是「前端直连数据库」的路径，而云函数这条路径必须靠代码自己保证 ——
> 所以 `tasks/index.js` 里每条 `where` / `update` / `remove` 都强制带 `_openid`（见第九节）。

## 四、建议索引

在 **云开发控制台 → 数据库 → 选中集合 → 索引管理 → 添加索引** 里建。
数据量小的时候不建也能跑，但每人几百条、总记录上万以后，没索引的查询会明显变慢甚至超时。

| 集合 | 索引字段 | 类型 | 为什么需要 |
|---|---|---|---|
| `tasks` | `_openid` | 单字段，**非唯一** | `list` 的主查询条件就是 `where({_openid})`，几乎所有操作都走它 |
| `tasks` | `_openid` + `date` | 组合，非唯一 | 按日期取某天/某周的日程（周视图），以及按日期排序 |
| `tasks` | `_openid` + `done` | 组合，非唯一 | 统计与「只看待办」的筛选 |
| `settings` | `_openid` | 单字段，**唯一** | 每人只应该有一条设置；设成唯一索引能挡住并发重复创建 |
| `reminders` | `_openid` | 单字段，**非唯一** | 定时扫描与页面查询都是 `where({_openid})`；**这张表会随提醒次数持续增长**，不加索引会越来越慢 |

> 索引字段顺序有讲究：**等值条件在前，范围/排序在后**。
> 所以组合索引一律把 `_openid` 放第一位 —— 它永远是等值匹配。
>
> `reminders` 的 `_openid` 索引**建议一次建好**：其它两张表的条数是有限的（任务数、一条设置），
> 而 `reminders` 每发一条提醒就多一行，是唯一会**单调增长**的集合。

## 五、`settings` 集合字段表

每人只有一条，由三组接口维护：`settings_save`（学期与作息）、`ai_config_*`（AI Key）、
`remind` 云函数的 `config` / `ack`（提醒开关与额度）。
**三组都复用同一个集合，不新建集合** —— 新建集合意味着用户还得去控制台手工建一次、设一次权限。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` / `_openid` | string | 自动 |
| `semester_start` | string \| null | 开学第一周的**周一**，`'YYYY-MM-DD'`。传周三也会被归到那一周的周一（与 Python 版 `monday_of` 一致）；清空传 `null` |
| `period_times` | object \| null | 作息表，键是节次字符串，值是 `["开始","结束"]`，如 `{"1":["08:00","08:45"], ...}`；最多 20 节，非法时刻会被丢掉 |
| `ai_provider` | string | **用户自选的服务商**，只允许 `'zhipu'` / `'deepseek'`，空串 = 用默认推荐那家。白名单外的值会被**拒绝**（不是忽略） |
| `ai_api_key` | string | **用户自填的 API Key（明文）**，空串 = 没填（等价于清除）。见下方安全说明 |
| `ai_model` | string | 用户覆盖的模型名，空串 = 用该服务商的默认模型。**识图时这里要填多模态模型**（如 `glm-5.3-flash` / `glm-ocr`） |
| `ai_updated_at` | string | 最后一次改 AI 配置的时间（与 `updated_at` 分开，便于页面显示"你上次更新时间"） |
| `remind_enabled` | boolean | 到期提醒总开关。**判定口径是"必须真值 `true`"**：没有这个字段（老用户从没配过）一律当**关闭**，不会被误开 |
| `remind_quota` | number | **剩余可下发条数**。微信的**一次性订阅**是"授权一次只能发一条"，所以用户每授权一次这里 **+1**，**每成功发出一条 -1**；为 `0` 时**绝不调用下发接口** |
| `lead_min` | number | 提前多久提醒（分钟），只接受 `15 / 30 / 60 / 120 / 1440` 之一；其它值一律回落到默认 **60** |
| `created_at` | string | 首次保存时间 |
| `updated_at` | string | 最后一次写这条记录的时间 |

**默认值：`settings_get` 不会替客户端回填任何默认值。**

* `semester_start` 没设置过 → 返回空字符串 `''`。
* `period_times` 没校准过 → 返回 **`null`**（**不是**一份内置作息表！）。

> 🔴 **为什么不回填内置作息表**（真机踩过的 bug，别再改回去）：
> 服务端曾把 `null` 回填成内置的 13 节默认作息。客户端拿到后把它当成"用户的当前作息"，
> 导入 `.ics` 时又拿它当**合并基准** → 内置默认值被当成"导入课表时自动校准的结果"
> **持久化到云上**。后果有两个：
> 1. 界面上第 6 节（`14:55-15:40`，正是内置默认值）永远显示「已校准」，
>    而用户的课表里根本没有第 6 节 —— **「已校准」这个标记不再诚实**；
> 2. 因为第 6 节"存在"，午休那一行就不被认成空档，**永远不会出现**。
>
> 正确分工：**服务端只回"用户真的存过什么"，内置默认作息由客户端显示时兜底**
> （客户端的 `utils/periods.js` 本来就这么做）。这样「已校准」只可能出现在
> 真的校准过的节次上。`normalize.js` 的 `DEFAULT_PERIOD_TIMES` 仍保留导出，
> 但**只作为文档/兼容常量**，不再回传给客户端。

> ⚠️ 注意**没有 `semester_start` 就算不出周次**，`stats` 的 `finished` 会恒为 `0`（无法判断第几周）。
> 所以「导入课表」这类功能应该顺手把 `semester_start` 一起存了。

### 关于 `period_times`（作息表）—— 它是怎么来的

**用户不手填作息表。** 它是**导入课表时自动校准**出来的（`utils/ics.js` 解析 `.ics` 时顺手算出每节课的上下课时间），
「我的」页把它**只读**展示，并给校准出来的节次打上「已校准」标记。

> **这里修过一个"屏幕上的行号是错的"的 bug**：导入时**算出了** `period_times`，
> 但**从来没写回 settings**，于是课表页一直用内置默认作息去算"这个时间属于第几节"。
> 用真实数据反推时，**3 条任务有 3 条结论不同**（典型：`12:00` 的截止在默认作息里落在午休空档、
> 任何一节都落不进去 → 掉进「其他时段」；在校准作息里应落第 5 节）。
> 现在两条导入路径（替换 / 追加）成功之后都会持久化它，
> 合并语义是**"新节次覆盖同名、未涉及的保留"**（不是整体覆盖），
> 且**导入成功与作息保存解耦** —— 作息没存上不会把导入说成失败。

### 关于 `ai_api_key`（用户自填的 Key）—— 安全说明

* **谁能读到**：集合权限是「仅创建者可读写」，所以只有用户本人（经前端直连）和**云函数**
  能读到。云函数用的是管理端权限、会绕过权限规则，所以它每条查询都强制带 `_openid`
  （见 `tasks/index.js` 与两个 AI 云函数）。
* **前端能不能读回原文**：**不能**。`ai_config_get` / `ai_config_save` / `ai_config_clear`
  一律只回 `masked`（形如 `****abcd`，只留末 4 位）与 `hasKey`，返回对象还额外过一遍
  `stripSecrets()`。Key **只在"保存"那一次**从客户端上传；之后每次 AI 调用都是
  `aiParse` / `aiDecompose` **自己按 `_openid` 去库里读**，不需要前端再传。
* **日志里有没有**：没有。日志只写 `来源=用户自填` / `来源=服务端环境变量`、
  服务商名、模型名与掩码；另有一层 `scrubSecret()` 兜底，把可能混进日志文本的
  `Bearer xxx` / 长 token 抹掉。
* **明文存的**：是明文（不是加密）。对一个小程序 + 数据库权限锁死的场景，这是刻意的权衡 ——
  加密需要一个额外的密钥管理设施（KMS），否则"加密密钥也存在同一个云函数里"，只是自我安慰。
  真要更严，请把 `settings` 的权限保持「仅创建者可读写」，并且**不要把导出的数据文件外传**。

## 五之二、`reminders` 集合字段表

这张表由 **`remind` 云函数**独占写入（小程序端只读，用来显示"发过什么"）。
它同时承担两件事：**幂等记账** 与 **失败留痕**。一条记录 = 一次下发尝试。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` / `_openid` | string | 自动。`_openid` 是归属，云函数每条查询都带它 |
| `task_id` | string | 对应 `tasks` 的 `_id`。测试下发时可能是占位值 |
| `due_key` | string | **幂等的关键**：一条任务在某个截止时刻上的唯一标识（形如 `<task_id>@<时刻>`）。发过就记下来，**同一个 `due_key` 不再发第二次** |
| `sent_at` | string | 这次尝试的时间，北京时间 ISO 串 |
| `template_id` | string | 当时用的订阅消息模板 ID（换过模板时能看出历史记录用的是哪个） |
| `type` | string | 固定 `'subscribe_message'`，用于区分以后可能加进来的其它记录类型 |
| `ok` | boolean | **`true` = 已发出；`false` = 尝试过但失败** |
| `error` | string | 失败原因（`ok:true` 时为空串）。**里面会写明"哪个字段、发出去的是什么值"** |

### 为什么失败也要记一条（而不是只记成功的）

微信的模板字段约束是**平台侧**规则：字段名对不对、`date` 类字段到底收不收
`2026年9月28日12:00` 这种"年月日+时刻"的形状，**本地照着官方文档示例去猜，无法完全预演**。
所以一旦微信回 `47003`（模板参数不合规），必须能一眼看到"**哪个字段、发出去的是什么值**"，
否则用户拿着 `argument invalid` 完全无法判断该改映射还是该改格式。这张表就是**唯一的自证手段**。

> **一条必须注意的口径**：`due_key` 的"已提醒"判定**只认 `ok:true` 的记录**。
> 如果失败记录也算作"已提醒"，那么用户把模板字段改对之后，这条提醒就**再也发不出来了**。

### 两个常见错误码（云函数会自动分类）

| errCode | 含义 | 云函数的处理 |
|---|---|---|
| `43101` | 用户拒收 / 没有有效授权（额度用完或用户在设置里关了订阅） | **自动关掉该用户的提醒**（`remind_enabled=false`）——否则每 5 分钟白跑一次；用户下次进小程序可重新授权 |
| `47003` | 模板参数不合规（字段名对不上、超长、格式不对） | 只留痕并给出排查提示（提示去核对 `REMIND_FIELD_MAP` 与字段类型），**不动**用户开关 |

> **平台限制（照实写）**：一次性订阅的**额度是消耗品**（授权一次只能发一条）；
> **长期订阅只对特定行业类目开放**，个人主体申请不到。
> 所以**没有模板时的降级方案是"小程序内提示"** —— 不依赖微信通知也能用。

## 六、课表导入：`import_replace` 与 `bulk_add` 去重

课表（`.ics`）导入有两个接口，**别搞混**：

| action | 语义 | 什么时候用 |
|---|---|---|
| `bulk_add` | **追加 + 去重**（重复的跳过，不报错） | 只想补几条；或者调用方不确定是不是重复 |
| `import_replace` | **替换**：先删旧课表，再插入新的 | 用户"重新导一份正确课表"（本接口就是为这个场景加的） |

### 6.1 `import_replace`

```
入参: { action:'import_replace', scope:'courses', tasks:[...] }
出参: { ok:true, removed:N, inserted:M, skipped:K, duplicates:D, errors:[...], partial:false }
```

* **`scope` 只接受 `'courses'`，而且是精确匹配**（区分大小写、不做 trim）。
  `'all'` / `'COURSES'` / `'courses '` 一律**拒绝**并说明原因。
  **刻意不提供"清空全部"的用法** —— 那种口子一旦存在，前端一个手滑就能清空用户全部数据，
  而用户还以为自己在"导课表"。想清空请让用户自己一条条删（或删掉整个集合记录）。
* `removed` 是**真实删掉的条数**，前端用它写确认框（"将替换 N 门课"）。
* `partial:true` 表示"删成功但插失败（或插少了）"。此时 `removed` 与 `inserted` 都是真实数字，
  前端应当提示"已删除 N 条、仅补回 M 条，请重新导入"。**不会假装成功。**
* `skipped` = 不合法条数 + 重复条数 + 写入失败条数；`duplicates` 单独给出重复条数。

#### 「课表类任务」的判据（**这条必须记住**）

> **`repeat === 'weekly'` 且 `periods` 非空。**

`scope:'courses'` 时**只能删这一类**。用户手工添加的日程、DDL、子任务
（`repeat='none'` 或没有节次）**一条都不会被删**。

两个**已知边界**，照实写在这里：

1. ⚠️ 用户**手工建的**"每周重复 + 填了节次"的任务，长得和课表一模一样，**会被一起替换掉**。
   这是可接受的（它确实就是课表形态），但要知道有这个可能。
2. ⚠️ `.ics` 里**没写节次**的 weekly 课（`periods` 为空串）**不算**课表类，
   因此**不会被替换删掉** —— 于是重复导入时它可能残留多条，需要手工删。
   这是刻意选的：**宁可少删（用户手工删一条），也不能因为"猜"而多删**（那会悄悄吞掉用户的数据）。

### 6.2 `bulk_add` 的去重

去重键 = **标题 + 日期 + 开始时间**（三者全等才算重复）：

* **为什么是这三个**：它们一起构成"用户眼里的同一条日程"（同一件事、同一天、同一时刻），
  重复导入课表时必然完全相同。不把 `end_time` / `location` / `estimate_min` 放进去，
  是因为用户改了这些细节不该算成"新的一条"（否则去重失效、又会翻倍）；
  **不把 `type` 放进去**，因为同一件事换个类型仍是同一条。
* **`start_time` 必须参与**：同一天同名但上午一场、下午一场是两件真事，不能误杀。
* 比较的是**归一化之后**的值，所以 `9:5` 与 `09:05`、`" 开会 "` 与 `"开会"` 都算同一条。
* 重复**不报错**，只计入 `skipped` / `duplicates`；`errors` 里只放真正不合法的数据。

## 七、数据量估算与免费额度

微信云开发的免费额度（个人版，具体以官方最新公告为准）大致是：

| 资源 | 免费额度 | 我们的用量估算 |
|---|---|---|
| 数据库存储 | 2 GB | 一条任务约 **0.5 KB**，1 万条才 ~5 MB → **完全够用** |
| 数据库读操作 | 5 万次/天 | `list` 一次调用最多 3~4 次读（分页）；`stats` 2 次。个人用几千次/天 |
| 数据库写操作 | 3 万次/天 | `bulk_add` 导入 100 条课表 = 100 次写（分批串行） |
| 云函数调用 | 免费额度按资源量计 | 日常个位数调用/人/天 |
| 云函数外网流量 | 有额度 | 只有 `aiParse` / `aiDecompose` 走外网调大模型，每次几 KB；**识图那条会传一张压缩过的图**（base64 字符数上限 90 万 ≈ 660 KB 原图），比文本大得多 |
| **订阅消息下发次数** | **不是额度制，是授权制** | 一次性订阅 = 用户授权一次只能发一条。所以「发得出去几条」取决于用户授权了几次，**不消耗云开发的资源额度** |

**省额度的几个实操点**：

* `list` 会**分页取全**（单次最多 100 条，循环取），不要在前端再轮询一次。
* 前端别在 `onShow` 里无脑 `list` + `stats` 各调一次；合并成一次 `stats` + 一次 `list` 就够。
* 每次 `add` / `update` 都是一次写操作 —— 拖拽排序那种高频交互要**攒着一起提交**（或用 `bulk_add`）。
* 超了额度会**拒绝服务**（报错而不是扣费），所以免费额度用尽时小程序表现为"所有按钮都失败"，
  排查方向就是控制台的「资源使用」页。

## 八、导出 / 导入 JSON 备份

### 导出（备份）

1. 云开发控制台 → **数据库** → 选中 `tasks` 集合。
2. 点右上角 **导出**（有的版本在「···」菜单里）→ 选择 **JSON** 格式 → 选导出路径 → 导出。
3. 对 `settings` 集合重复一次。
4. 导出文件是一个 `.json`（内容形如 `{"_id":"...","_openid":"...",...}` 每行一条），**存到云盘之外的地方**。

> 导出的是**全库**数据（包含所有人的 `_openid`），属于敏感文件，别随手丢在公共目录。
>
> 🔴 **`settings` 的导出文件里还包含用户自填的 AI Key 原文**（`ai_api_key` 字段，
> 见第五节）。导出的 JSON 就是**明文凭证的集合**：
> * 不要放进 git 仓库、群聊、云盘共享链接、演示材料或截图里；
> * 备份完就挪到只有你能访问的位置，确认不再需要时**彻底删除**；
> * 万一泄露了，第一件事是去对应服务商后台**吊销那些 Key**（用户自己填的 Key 只能由用户吊销，
>   所以必要时得通知他们），而不是只删文件。
> * 只想备份任务数据、不想碰凭证的话：导出 `tasks` 集合即可，`settings` 里的
>   `semester_start` / `period_times` 很小，必要时手抄一份就行。

### 导入（恢复）

1. 云开发控制台 → **数据库** → 选中 `tasks` 集合。
2. 点 **导入** → 选 JSON 文件 → 选 **冲突处理方式**：
   * `_id` 相同 → **跳过**（安全的加法导入，推荐）
   * 想整表覆盖就先用「清空集合」再导入
3. ⚠️ **导入要保留 `_openid` 字段**，否则恢复出来的数据没有归属，谁都读不到
   （云函数所有查询都带 `_openid` 条件）。控制台的导入默认会带上文件里的 `_openid`。

### 用云函数导出（可选，适合定期备份）

如果不想每次手工点控制台，可以自己加一个只读的导出 action —— 但我们**没有**加，
因为它会一次性读出当前用户全部数据，容易踩到云函数 1 MB 返回体上限。
数据量超过 1000 条时，建议还是用控制台导出。

## 九、为什么不能把 openid 交给前端

这是整个项目**最重要的一条安全规则**：

```js
// ✅ 唯一正确的取法：由微信在调用链路上注入，前端伪造不了
const { OPENID } = cloud.getWXContext();

// ❌ 绝对不要这样：event.openid 完全由前端控制
const openid = event.openid;
```

* **前端传的 `openid` 就是攻击者的输入。**
  小程序代码在用户手机上，`wx.cloud.callFunction({ data: { openid: '别人的' } })` 一行就能改。
  一旦云函数信任这个字段，改一个字符串就能**读到全库所有人的日程、改掉、甚至删光**。
* **`getWXContext().OPENID` 是微信云托管在校验用户登录态后注入的**，
  它对应真实的 `wx.login` 会话，前端**没有任何办法**篡改。
* **所以本项目规定**：
  1. 用户身份**只**来自 `cloud.getWXContext().OPENID`；
  2. 每条查询 / 更新 / 删除都**必须**带 `_openid` 条件（哪怕 `_id` 已经唯一了）：
     ```js
     // 哪怕前端传了别人的 _id，这个条件也只会"匹配不到"
     db.collection('tasks').where({ _openid: OPENID, _id: id }).update({ data: patch })
     ```
  3. `update` 的 patch 走**字段白名单**，`_openid` / `_id` / `created_at` 这些键**永远**写不进去；
  4. 前端连"自己的 openid"都不需要知道 —— `utils/api.js` 里一个 openid 参数都没有，这是**故意的**。
* **`updated === 0` 就等于"无权修改"**：所有写操作的判定口径统一成"改到了 0 条 → 判定为不存在或无权"，
  绝不会因为"没改到"就顺手创建一条（那正好会被用来给别人的账号里塞数据）。

> 自查方法（本仓库真的会跑）：
> ```bash
> cd miniprogram/cloudfunctions
> node _selftest.js        # 里面有 "前端伪造 openid 无效" / "越权 update 造不出记录" 的断言
> ```

## 十、从 Python 版搬过来时的取舍（给未来的自己看）

参考实现是 Streamlit 版 `smart-scheduler`（`task_manager.py` / `config.py` / `storage.py`）。
搬到小程序云开发后有几处刻意的不同：

| 点 | Python 版 | 小程序版 | 为什么 |
|---|---|---|---|
| 多用户隔离 | SQLite `space` 空间码（`?u=xxxx`），**免注册** | 云数据库 `_openid` 字段 | 小程序天然有微信身份，不需要自己造空间码；`_openid` 由平台注入，比 URL 参数可信 |
| 时区 | `date.today()` 用容器本地时区 | **固定按北京时间 UTC+8 折算** | 云函数容器是 UTC，直接取 `toISOString()` 会在北京时间 00:00~08:00 之间算错一天 |
| 任务主键 | 自增整数 `id` | 云数据库 `_id`（字符串） | 分布式环境下自增 id 需要额外维护计数器，云数据库自带主键更省事；`parent_id` 因此变成字符串 |
| `stats.finished` | `is_task_finished` 按"最后一次课是否上完"判定 | **同一套算法**（`last_occurrence_date` + 单双周倒推 + 当天下课时间） | 口径必须一致，否则同一份课表在两端算出的"已结课"数量不同 |
| `done` 与 `finished` | `done` 的任务不再计入 `finished` | 同 | 避免一门课被同时算进"已完成"和"已结课" |
| 写入粒度 | 整表覆盖写（`save_tasks` 全量落盘） | 单条 `add` / `update` / `remove` | 云数据库按条计费，全量覆盖既慢又费额度 |
| 批量写 | 无限制 | **20 条一批**串行提交 | 云数据库单次批量写有限制，超了会报错 |
| 读取 | 一次读全 | **100 条一页循环取** | 云数据库单次 `get` 最多 100 条 |
| `settings` | `data/settings.json` 全量 | 每人一条独立记录 | 多用户下不能共用一份设置 |
| AI 调用 | Python `requests` | Node 内置 `https` | 项目要求**不引入任何额外 npm 依赖**，所以没用 axios / node-fetch |
| AI 服务商 | 硬编码 DeepSeek（`config.py` 的 `BASE_URL` + `MODEL`） | **服务商表 + 环境变量**：智谱 `glm-4.7-flash` 为主、DeepSeek 备选 | 换服务商不该改代码；「谁配了 Key 用谁」保证换了默认家也不会让老 Key 失效（见《部署云函数.md》第 2 节） |
| AI 失败提示 | 区分"未配 key"/"缺少依赖"/"解析失败"三种文案 | 统一 `AI 服务暂不可用`（细节只写日志） | 契约要求统一返回 `{ok:false, error:'AI 服务暂不可用'}`；两家错误码语义不同，细节放日志里排查 |
| 服务端校验 | 宽松（本机单用户，信任输入） | **严格**：白名单 + 时间/日期格式校验 + 长度截断 | 小程序前端不可信；脏数据一旦入库，后续统计全错 |
| 提醒 | 无（Python 版没有服务通知） | **`remind` 云函数**：每 5 分钟定时扫描 + 微信订阅消息，额度制 + 幂等 | 手机上"提醒"必须走微信的服务通知通道，且一次性订阅的额度是平台规则，只能按它来 |
| 集合数量 | `data/schedules.json` + `data/settings.json`（两个文件） | **三个集合**：`tasks` / `settings` / `reminders` | 提醒的记账独立成一张表：它是唯一会**单调增长**的数据，混进 `settings`（每人一条）会撑坏它 |

**保留一致的部分**：`_normalize_task` 的容错规则（非法类型/优先级回退、DDL 只留截止时刻、
`estimate_min` 负数归 0、不重复的任务不存周次）、`get_task_stats` 的口径、以及
`ai_parser.py` 的两段中文 prompt 与容错 JSON 解析（尾逗号 / 全角引号 / 代码块围栏 / 前后废话）。
