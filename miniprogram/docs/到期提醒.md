# 到期提醒（微信订阅消息 / 服务通知）

> 目标：DDL 快到期时，给用户推一条**微信服务通知**。
> 这个能力**一半在云端（已完成）、一半要你在微信后台手动配置**——本文按顺序写清每一步。
>
> 代码位置：`cloudfunctions/remind/`（云函数）、契约见本文末尾「前端需要做什么」。
> 纯逻辑自测：`node cloudfunctions/_selftest.js`（第 10 节覆盖 `remind`）。

---

## 0. 一句话原理（先看懂这个，后面就不容易配错）

小程序**不能**自己定时唤起自己。所以做法只能是：

```
云函数 remind 的定时触发器（每 5 分钟）
      ↓  扫所有「开了提醒」的用户
      ↓  找出「即将到期 且 还没提醒过」的 DDL（截止事项）
      ↓  云调用 openapi.subscribeMessage.send
   微信服务通知 → 用户手机
```

三个**无法绕过**的平台约束（配之前必须接受）：

| 约束 | 后果 | 我们的应对 |
|---|---|---|
| 订阅消息必须**用户主动授权**才能发，且**授权一次只能发一条**（一次性订阅） | 用户不许一次，就一条都发不出去 | 用户每开一次开关 = 攒 1 条额度；额度用完就**停止下发**，下次进小程序再引导补授权 |
| 模板必须从**公共模板库**选、**审核通过**才有 templateId | 没模板 = 功能整体不可用 | 服务端没配模板 ID 时 `scan` 直接返回 `ok:false` 说明原因，**不去调用微信接口**（避免无意义的失败日志） |
| 长期订阅（授权一次可长期发）**只对特定行业类目开放** | 工具类小程序一般**拿不到** | 老实按一次性订阅做，不假装能长期发 |

> 官方依据：
> [发送订阅消息](https://developers.weixin.qq.com/miniprogram/dev/server/API/mp-message-management/subscribe-message/api_sendmessage.html)、
> [定时触发器](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloud/guide/functions/triggers.html)。

## 2. 给 `remind` 云函数配置环境变量

云开发控制台 → **云函数 → remind → 配置 → 环境变量**，新增：

| 变量名 | 必填 | 值 | 说明 |
|---|---|---|---|
| `REMIND_TEMPLATE_ID` | ✅ | `Tie4p47PRO5I8cuu8LktzXgjgfvTJL4HrkAXiZwHY2s` | **没有它整个功能不工作**（`status` 会返回 `ready:false` 并说明原因） |
| `REMIND_FIELD_MAP` | ⬜ | **不用配** | 默认映射已经对齐下面这个模板。**换模板时才需要写**（见下一节） |
| `REMIND_PAGE` | ⬜ | 默认 `/pages/tasks/tasks` | 用户点通知后打开的小程序页面 |

**这个模板 ID 就是你要填的值**（用户已申请到的那个）：

```
REMIND_TEMPLATE_ID=Tie4p47PRO5I8cuu8LktzXgjgfvTJL4HrkAXiZwHY2s
```

它对应的模板字段（前后顺序就是微信里的展示顺序）：

| 字段 | 模板里的名字 | 我们的语义槽位 | 实际发出去的样子 |
|---|---|---|---|
| `{{thing2.DATA}}` | 提醒内容 | `title` | `提交实验报告`（权重 12 / 上限 20） |
| `{{date4.DATA}}` | 日程时间 | `due` | `2026年10月13日`（**纯日期**；带时刻会被拒，代码会自动降级并记住，见 §2.6） |
| `{{short_thing19.DATA}}` | 日程类别 | `category` | `截止` / `日程`（权重 4 / 上限 5） |

> **标题栏不带"（还剩 N 分钟）"** —— 不是没想到，是**平台字段放不下**：
> `thing` 的上限 20 是**权重**（汉字算 2），真实预算只有 ≈10 个汉字，
> 而"（还剩30分钟）"自己就占 12 权重。详见 §2.6「长度是按权重算的」。
> "还剩多久"由 `date4`（日程时间）表达。

> **默认映射已对齐这个模板，`REMIND_FIELD_MAP` 不配也能用。**
> 不放心的话部署后调一次 `status`，看返回里的 `field_preview_text` 是不是
> `thing2=… | date4=… | short_thing19=…` 这三项。

### 换模板时 `REMIND_FIELD_MAP` 怎么写（只在换模板时才需要）

* **键（左边）** = 你模板里的字段名，必须长成 `类型名 + 数字`：`thing1` / `short_thing19` /
  `date4` / `time2` / `character_string1` 这样。
* **值（右边）** = 语义槽位，**只能是这四个之一**：
  * `title` → 任务标题（超长会按权重裁到该字段上限内）
  * `due` → 截止时刻
  * `left` → 剩余时间
  * `category` → 任务类别（`截止` / `日程` / `子任务`）
* 例：新模板字段是「事项名称 `thing1`、截止时间 `time3`、提示 `thing4`」：
  ```json
  {"thing1":"title","time3":"due","thing4":"left"}
  ```
* 写错的后果：**不会**让功能整体挂掉，而是那条字段被忽略 + `status`/`scan` 返回里出现
  `config_warnings`（例如"模板字段名 xxx 形状不对，已忽略"）。全部写错时会回退到默认映射。

### 字段类型前缀对照表（决定长度与格式）

微信的字段类型由 **key 的前缀**决定，每种的约束不同。**发错类型 = 47003**，所以这张表是排查的起点。

**⚠️ 下表"上限"一列的单位是权重，不是字符数**（见 §2.6）：汉字/全角标点算 **2**，
数字/字母/半角符号算 **1**。所以 `thing` 的 20 权重 ≈ **10 个汉字**。

| 类型前缀 | 含义 | 上限（**权重**） | 折合汉字 | 格式要求 | 我们会不会用它放标题 |
|---|---|---|---|---|---|
| `thing` | 短语/事项名 | **20** | ≈10 个 | 可带空格 | ✅ 首选 |
| `short_thing` | 短事项名 | **5** | **2 个** | 不能有空格 | ⚠️ 只放得下 2 个汉字 |
| `phrase` | 汉字短语 | **5** | 2 个 | 不能有空格 | ❌ 放不下标题 |
| `date` | 日期 | — | — | `2026年9月28日12:00`（年月日，**不补零**） | — |
| `time` | 时间 | — | — | `12:00` 或 `2026年9月28日12:00` | — |
| `character_string` | 数字/字母/符号 | **32** | — | 不能有空格 | ❌ 放标题会被拒 |
| `number` | 数字 | 32 | — | 数字 | — |
| `amount` / `name` / `phone_number` / `car_number` / `letter` / `symbol` | 各类专用关键字 | 12 / 10 / 20 / 8 / 6 / 5 | — | 各自格式 | ❌ |

代码里的处理：**超长一律由我们主动按权重截断**（截断处补 `…`，省略号也占 2 权重，
按码点遍历所以 emoji 不会被切一半），不允许空格的类型把空格换成 `·`，
`date`/`time` 型自动改成上面那种年月日形状 ——
全部都是为了让微信**收下**这条消息，而不是等它回 47003。
被截断的字段会出现在 `buildMessageData` 的 `truncated` 与 `status.config_warnings` 里，
**不会悄悄截短**。每个字段发出去之前还会过一遍 `checkFieldCompliance()` 本地自检。

> **为什么模板 ID 只放服务端、前端不硬编码**：换模板只改这一个环境变量，
> 不用重新提交小程序审核。前端通过 `status` action 把 `template_id` 取走再去弹授权窗。

> ⚠️ **改完环境变量必须重新部署一次云函数**才生效（和 `aiParse` 的 Key 一个道理）。

## 2.6 【真机证实】长度是按「权重」算的，不是字符数

这一条是**真机实测**得到的结论，不是推测。第一次真机点「发一条测试提醒」，微信原样返回：

```
openapi.subscribeMessage.send fail: argument invalid data format,
invalid value of property: data.thing2, should be 5-20 characters
示例：{"data":{"thing2":"..."}}
```

我们当时发出去的值（正是靠 `reminders` 里那条 `ok:false` 记录才看到的）：

```
thing2=提交实验报告（还剩30分钟） | date4=2026年10月12日23:54 | short_thing19=截止
```

**按码点数，`提交实验报告（还剩30分钟）` 只有 14 个字符**，看着完全没超 20，为什么被拒？
把它按"汉字/全角算 2"重新算一遍：

| 部分 | 权重 |
|---|---|
| `提交实验报告`（6 个汉字） | 12 |
| `（`（全角括号） | 2 |
| `还剩`（2 个汉字） | 4 |
| `30`（半角数字） | 2 |
| `分钟`（2 个汉字） | 4 |
| `）`（全角括号） | 2 |
| **合计** | **26** |

26 > 20，与微信那句 `should be 5-20 characters` 完全吻合。⇒ **`thing` 的 "20" 是权重，
真实预算只有 ≈10 个汉字。**

由此产生的三个改动（都已落在代码里）：

1. **判定与截断统一走权重**：`fieldUnits(text)` = 汉字/全角标点 2 + 其余 1；
   超限时 `truncateToUnits()` 从尾部按码点裁、补 `…`（省略号自己也算 2），
   并保证**结果一定合规**（`checkFieldCompliance()` 自检，有回归用例）。
2. **`short_thing` 的 5 权重只够 2 个汉字**：所以 `截止`(4) / `日程`(4) 合规，
   而 `子任务`(6) **超**，会被自动裁成 `子…`。以后有人往里填 3 个汉字，同样会被裁 ——
   这是刻意的（不发出去，比发一条超限被整条拒掉好）。
3. **去掉了「（还剩 N 分钟）」尾巴**：它占 12 权重、吃掉一半以上预算，
   加上它之后稍长的标题必然超限 → **整条消息发不出去**。"还剩多久"由 `date4` 表达。

### 【真机证实】`date` 类字段**不吃"年月日 + 时刻"**

修好 `thing2` 之后重新部署、再点一次测试，微信这次报的是**另一个字段**：

```
openapi.subscribeMessage.send fail: argument invalid data format,
invalid value of property: data.date4
```

我们当时发的值（同样来自 `reminders` 里那条记录）：

```
thing2=【测试】到期提醒 | date4=2026年10月13日00:09 | short_thing19=截止
```

注意两点：

* `thing2=【测试】到期提醒` 是 **16 权重**，这次**没被挑错** → 上一轮的权重口径是对的；
* 微信只说 `invalid data format`，**没给期望形状**。

⇒ 结论：**`date` 类收哪种形状，代码层面猜不出来，只有真机能判定。**

所以代码**不再猜**，改成"先用信息量更大的、被拒就降级并记住"：

| 步骤 | 行为 |
|---|---|
| 1. 首次发送 | 用**带时刻**的形状 `2026年10月13日00:09`（官方示例 `2019年10月1日15:01` 那种） |
| 2. 被点名拒绝 | 只有错误里**点名的是 `date` 类字段**时才降级：换成**纯日期** `2026年10月13日` **重试一次** |
| 3. 重试成功 | 把 `remind_date_style = 'date'` 写进该用户的 settings，**后续直接按纯日期组装**（不再浪费一次失败尝试） |
| 4. 两次都失败 | 把**两次**的字段值与错误码都带出来（只留最后一次的话，"哪种形状不行"这个结论就丢了） |

**边界（刻意收窄，避免"用重试掩盖真问题"）**：

* 错误点名 `thing2` 等**非 date 字段**时**绝不重试** —— 那是真问题，重试只会把它伪装成"两次都失败"；
* 已经是纯日期了就不再重试（无从再降）；
* 43101（用户拒收）之类的非参数错误也不重试；
* 重试**只影响 date 类字段**，`thing2` / `short_thing19` 的值逐字不变（有断言）。

**额度只扣一次**：失败那次的额度按 §2.5 的规则退回，只有重试成功那次才真正扣。
所以整条链路（发两次、成功一次）的额度净变化恒为 **-1**，`scan.quota_refunded` 与
记录里的 `quota_refunded` 会把"退过一次"如实报出来。

> **这不是"我们猜对了格式"**：是**平台自己告诉我们、并且只问一次**。
> 代码里没有写死"date 必须是纯日期"这种假设 —— 万一哪天微信又收带时刻了，
> 把该用户 settings 里的 `remind_date_style` 清掉即可回到带时刻（信息量更大的那种）。

## 2.5 第一次真机发送失败怎么办

**排查顺序：先看 `reminders` 集合里那条 `ok:false` 记录，再对着类型约束改。**
每条失败记录都带了 `sent_fields`（字段名、类型、槽位、**实际发出去的值**）——
这是唯一能自证"到底哪个字段、发了什么"的东西（模板约束是平台侧的，本地无法完全预演）。

```
reminders 集合里找最近一条 ok:false 的记录：

  error        : 模板参数不合规（47003）… 本次发出的字段与值：thing2=提交实验报告 | date4=2026年9月28日12:00 | short_thing19=截止
  err_code     : 47003
  quota_refunded: true          ← 这次占用的额度已经退回（配置类错误不该烧用户的授权）
  sent_fields  : [ {key:"thing2", type:"thing", slot:"title", value:"提交实验报告"},
                   {key:"date4",  type:"date", slot:"due",   value:"2026年9月28日12:00"},
                   {key:"short_thing19", type:"short_thing", slot:"category", value:"截止"} ]
```

云函数日志里也有一行同样的内容（`[remind] 下发失败（err_code=47003，额度已回退=true），本次字段与值：…`），
控制台点一次「云端测试」跑 `{"action":"test"}` 则会**直接把它放进返回的 `error` 里**。

### 两种错要分开看

| | **47003 = 模板参数不合法** | **43101 = 用户拒收 / 无有效授权** |
|---|---|---|
| 谁的锅 | **配置**（字段名对不上、类型不对、值格式不对、**超长**） | **授权**（用户点了拒绝，或额度早已用完） |
| 表现 | `sent` 一直是 0，`errors` 里有 47003 | 同上，但码是 43101 |
| 额度怎么算 | **退回**（`quota_refunded: true`）—— 微信侧根本没消耗，扣掉就是白扣；不退回的话模板配错一次，之后每 5 分钟白扣一次，几轮就把用户授权烧光 | **不退** —— 用户确实拒收了，额度本来就是无效的 |
| 云函数会做什么 | 只记录，**不动**用户的开关（改好配置下一轮自动恢复） | **自动把该用户的 `remind_enabled` 关掉**（否则每 5 分钟白跑一次），并把原因写进 `remind_disabled_reason` |
| 你该做什么 | 对照 `sent_fields` 与下面三条改 | 让用户重新进小程序点一次「开启提醒」补授权 |

### 47003 的具体改法（按可能性排序）

1. **值超长（最常见）** —— 记住上限是**权重**不是字符数：`thing` 20 权重 ≈ 10 个汉字。
   本地已经会主动按权重裁，所以走到真机还被判超长，通常是：
   * 你手改了 `REMIND_FIELD_MAP`，把标题指到了更小的字段（`short_thing` 只有 5 权重 = 2 个汉字）；
   * 或者模板里那个字段的类型和我们假设的不一样（对照 §2.6 的表）。
2. **字段名对不上** —— 把 `sent_fields` 里的 `key` 和微信后台模板里的字段名**逐字**对照，
   差一个数字就会 47003。改 `REMIND_FIELD_MAP` 后**重新部署**。
3. **`date` 类的形状被拒**（**已由真机证实**：`date` 不吃"年月日 + 时刻"）——
   * **代码已经自动处理**：被点名拒绝时会自动降级为**纯日期**并重试一次，
     成功后把 `remind_date_style='date'` 记住，后续直接按纯日期发（详见 §2.6）。
   * 你要做的：**什么都不用做**。若想核对，看 `status` 返回的
     `date_style` / `date_style_learned`，或 `field_preview_text` 里 `date4=` 后面有没有时刻。
   * 想回到"带时刻"（万一哪天微信又收了）：把该用户 settings 里的 `remind_date_style` 删掉即可。

> **诚实标注（已证实 / 未证实分开写）**：
> * ✅ **已由真机证实**：`thing` 的上限是**权重**（§2.6）；`date` 类**不吃"年月日+时刻"**（本节第 3 条）。
> * ⚠️ **仍未证实**：其它类型的数值（`short_thing` 5 / `phrase` 5 / `character_string` 32 …）
>   是按官方示例与通行规则写的；`short_thing19` 至今**没被证伪**（它每次都被一起发出去，
>   但整条消息是因别的字段被拒的）。
> 每次真机发一条测试提醒，`reminders` 里那条记录就是新的证据 ——
> **两轮真机各修正了一条假设**，这个机制值得留着。

## 3. 部署 `remind` 并确认触发器 / 云调用权限生效

1. 资源管理器里**右键 `cloudfunctions/remind` 目录** → **「上传并部署：云端安装依赖（不上传 node_modules）」**。
2. **确认云调用权限**：`remind/config.json` 里已经写好
   ```json
   { "permissions": { "openapi": ["subscribeMessage.send"] } }
   ```
   没有这段权限，云调用会以「无权限」失败（错误信息里会带 `openapi` 字样）。
   > 这一项在微信开发者工具里部署时随 `config.json` 一起生效；如果控制台里能看到
   > 「云调用 / 权限」列表，确认 `subscribeMessage.send` 在里面。
3. **确认定时触发器**：
   * 云开发控制台 → **云函数 → remind → 触发器**，应该能看到一个名为 **`remindScan`** 的
     **定时触发器**，并且显示**下一次触发时间**。
   * 配置来自 `config.json`：
     ```json
     { "triggers": [{ "name": "remindScan", "type": "timer", "config": "0 */5 * * * * *" }] }
     ```
   * **cron 是 7 位**（秒 分 时 日 月 周 年），所以 `0 */5 * * * * *` = **每 5 分钟**的第 0 秒触发。
     > 依据：[官方定时触发器文档](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloud/guide/functions/triggers.html)
     > —— "Cron 表达式有七个必需字段，按空格分隔"：秒 0-59 / 分 0-59 / 时 0-23 / 日 1-31 / 月 1-12 / 周 0-6 / 年 1970-2099。
     > 第七位（年）用 `*` 表示每年。**别写成 Linux 的 5 位 cron**，那样在控制台是配不上的。
   * 如果控制台显示触发器**没生效**：把 `config.json` 删掉重新部署一次；
     或者在控制台**手动**新建一个同名定时触发器（配置填同一串 cron）。
4. **手动跑一轮**（不用等 5 分钟）：控制台 → 云函数 → remind → **云端测试** →
   入参留空 `{}` 或填 `{"action":"scan"}` → 执行。
   返回里能看到本轮干了什么：
   ```json
   { "ok": true, "scanned": 1, "sent": 1, "skipped": 0, "failed": 0,
     "errors": [], "warnings": [], "skipped_reasons": {}, "details": [...] }
   ```
   * `scanned` = 扫了几个开了提醒的用户；`sent` = 真发出去几条。
   * 全 0 且 `ok:true` 通常是**正常的**（没有"5 分钟内即将到期"的 ddl）。想造一条：
     在小程序里新建一个 ddl，日期=今天、截止时间=**当前时间 + 10 分钟**，并且先在
     「我的 → 到期提醒」里打开开关并授权。

## 4. 真机验证步骤（**必须真机，不要用模拟器**）

服务通知是**微信客户端**的行为，开发者工具里看不到。

1. 用**你自己的微信**扫码打开**开发版**或**体验版**小程序（真机预览）。
2. 进「我的 → 到期提醒」→ 打开开关 → 微信弹出「订阅消息」授权框 → 点 **允许**。
   * 如果**没弹**授权框：说明 `wx.requestSubscribeMessage` 没调成功（多半是
     `template_id` 没从 `status` 拿到，或模板 ID 不是这个小程序的）。
   * 如果弹出但显示「该功能未开启 / 模板不存在」：模板 ID 抄错了，或模板还没审核通过。
3. 在小程序里新建一条 ddl：**日期 = 今天**，**截止时间 = 现在 + 10 分钟**。
4. 到云开发控制台**手动跑一次** `{"action":"scan"}`（或等定时器，最多 5 分钟）。
5. **看两个地方**：
   * 云函数返回：`sent` 应为 `1`。若是 `0`，看 `skipped_reasons` 和 `errors`（含义见第 7 节）。
   * 手机：返回微信 → 首页下拉 / 「服务通知」会话里应出现一条消息，标题是你的
     小程序名，内容是「任务标题 + 截止时间 + 还有 N 分钟到期」。
6. **点那条通知**，应该打开 `REMIND_PAGE`（默认 `/pages/tasks/tasks`）。
7. 再跑一次 `scan`：`sent` 应该是 **0**（幂等生效 —— 同一条 ddl 不会提醒两次）。

> **不要写成"一定能收到"**：能否收到取决于 ① 模板审核通过 ② 用户真授权了
> ③ 手机微信没关这个服务号的通知 ④ 微信侧风控。所以**验证要留证据**：
> 云函数返回的 `sent` 数字 + 手机截图，缺一不可。

### 授权额度是消耗品（这是最容易困惑的一点）

* 用户点一次「允许」= **+1 条**额度，只能发**一条**。
* 发成功后额度自动 -1；额度为 0 时**绝不调用下发接口**，而是记 `skipped: 'no_quota'`。
* 所以"用户授权了但第二天没收到"通常是**额度早就用完了** —— 前端应在用户下次打开
  小程序时（`status.ready === false` 且 `quota === 0`）再引导授权一次。
* 一次授权可以勾最多 3 个模板位（`ack` 的 `count` 允许 1..3）；
  为避免用户攒一堆额度变骚扰，服务端把总额**封顶 10 条**。

## 5. 平台限制（照实说，别指望绕过去）

| 限制 | 具体表现 | 是不是我们能改的 |
|---|---|---|
| 一次性订阅 = 授权一次只能发一条 | 用户不点授权，一条都发不出；额度用完就停 | ❌ 平台硬限制。只能反复引导授权 |
| 长期订阅只对特定行业类目开放 | 「工具」类小程序在公共模板库里**看不到**长期订阅模板 | ❌ 平台硬限制。要长期订阅得先有对应类目（多数个人小程序没有） |
| 模板必须审核通过才有 templateId | 选了模板也要等审核；审核不通过就没 ID | ❌ 要走后台流程 |
| 定时器最小粒度 | 5 分钟一轮，所以"提前 15 分钟提醒"实际可能落在到期前 10~15 分钟 | ✅ 已用 `GRACE_MS`=10 分钟宽限兜底，不会漏发 |
| 一周内可发条数上限 | 微信对用户侧的订阅消息总量有风控 | ❌ 平台侧，我们每轮每用户最多 3 条、总额封顶，已经尽量温和 |

## 6. 没有模板时的降级方案（**前端做，云端已准备好数据**）

如果类目不符 / 审核不通过 / 你不想走这个流程，功能**不必砍掉**，退化成「小程序内提醒」：

| | 服务通知（主方案） | 小程序内提醒（降级） |
|---|---|---|
| 提醒时机 | 到期前 N 分钟，用户不用打开小程序 | 用户**打开小程序时**看到「即将到期」 |
| 需要后台配置 | 模板 ID + 环境变量 + 触发器 | **什么都不用** |
| 谁负责 | 云端（已完成） | **前端**（本轮不做） |

**分工说明（重要）：**

* **云端（`remind` 云函数，已完成）**：
  * `status` 返回 `ready:false` + `ready_reason`（人话）—— 前端据此决定显示哪种提醒；
  * `status.lead_min` / `lead_options` 给出提前量设置项；
  * 纯函数 `dueInstantOf` / `planReminders` 与页面内提醒**同一套判断口径**：
    "哪些 ddl 即将到期"在云端和前端应当是同一个答案。
* **前端（`pages/`，本轮不做，由负责页面的同学实现）**：
  1. 「我的 → 到期提醒」卡片：开关 + 提前量选择（15/30/60/120 分钟、1 天）；
  2. 开启时调 `status` 拿 `template_id`，再调 `wx.requestSubscribeMessage`，
     成功后调 `ack` 上报授权条数；
  3. `status.ready === false` 时把 `ready_reason` 原样显示（那是给人看的话）；
  4. 无论有没有模板，**页面里都要有一套「即将到期」列表**（降级路径）。

> **本轮的边界**：`pages/` 由别人并行修改，所以本文只写契约与分工，
> 页面实现不在这里。契约以「前端需要做什么」一节为准。

## 7. 排查：按返回里的字段找原因

`scan` 的返回里有 `sent / skipped / failed / errors / skipped_reasons / details`，
`status` 的返回里有 `ready / ready_reason`。对照下表：

| 现象 | 去哪儿看 | 原因 / 处理 |
|---|---|---|
| `scan` 返回 `ok:false`，`error` 里说"还没配置订阅消息模板 ID" | `scan.error` | 第 2 步的 `REMIND_TEMPLATE_ID` 没配 / 没重新部署 |
| `skipped_reasons.no_quota` 很大 | `scan.skipped_reasons` | 用户授权额度用完了 —— **正常现象**，前端要引导补授权 |
| `skipped_reasons.already_sent` | 同上 | 幂等生效：这条 ddl 已经提醒过了（**这是对的**） |
| `skipped_reasons.too_early` | 同上 | 还没到提醒窗口（`lead_min` 之外的），下一轮再说 |
| `skipped_reasons.too_late` | 同上 | 过期超过 10 分钟宽限，放弃补发（避免"你早就过期了"的骚扰） |
| `errors` 里有 `47003` 字样 | `scan.errors` | **模板字段不合法**：错误里已经带上了「本次发出的字段与值」（`thing2=… \| date4=… \| short_thing19=…`），拿它和微信后台模板**逐字**对照。详细改法见 §2.5 —— 特别是"`date4` 只给日期"那条 |
| `errors` 里有 `43101` 字样 | 同上 | **用户拒收 / 没有有效授权**。此时云函数已自动把该用户的 `remind_enabled` 关掉（否则每 5 分钟白跑一次），用户重新授权即可恢复 |
| `errors` 里有 `40001` / `42001` | 同上 | access_token 问题，云调用会自动重试一次；持续出现请重新部署 |
| 不确定"到底会发出去什么" | `status.field_preview_text` | 用一条样例任务算出的最终字段与值，**不消耗额度、不碰真机**，部署后第一时间就能自查。**降级之后这里也会跟着变成纯日期**（`date_style` 一并返回） |
| 用户说"什么都没收到" | `reminders` 集合 | 每条下发尝试（成功**和**失败）都在这里留了一条记录，字段 `ok` / `error` / `err_code` / `sent_fields` 就是答案 |
| 定时器根本没跑 | 控制台触发器列表 | 看"下一次触发时间"有没有值；没有就按第 3 步重建触发器 |

### `reminders` 集合（新建，**别忘权限**）

权限同样设为 **「仅创建者可读写」**（和 `tasks` / `settings` 一致）。字段：

| 字段 | 说明 |
|---|---|
| `_openid` | 收件人（云函数显式写入） |
| `task_id` | 任务 id |
| `due_key` | **幂等键**，形如 `任务id@2026-10-16 12:00`。同一任务的同一截止时刻只会提醒一次 |
| `sent_at` | 下发时间（北京时间字符串） |
| `template_id` | 当时用的模板 |
| `type` | `subscribe_message`（扫描触发）/ `test`（测试触发） |
| `ok` | `true`=微信接受了；`false`=失败（**只有 `true` 才算"已提醒"**） |
| `error` | 失败原因（已脱敏）。失败时末尾会附上「本次发出的字段与值」 |
| `err_code` | 微信错误码 |
| `date_style` | 这次用的日期形状：`datetime`（带时刻）/ `date`（纯日期，真机证实可用的那种） |
| `quota_refunded` | 这次占用的额度有没有退回（配置/参数类失败会退，见 §2.5） |
| `attempts` | 成功时是次数（2 = 降级重试后才成功）；**失败时是数组**，逐次记下 `{index, date_style, err_code, sent_fields}` |
| `sent_fields` | **失败时才有**：`[{key, type, slot, value}]` —— 逐字段的实际取值，排查 47003 就看这个（单个值最多 60 字符，**不含 openid / 密钥**） |

> 建议索引：`_openid`（等值）。见 `docs/数据库与索引.md` 的索引口径。

## 8. 前端需要做什么（契约速查）

云函数：`remind`，调用方式与其它云函数一致（`utils/api.js` 的 `callCloudFunction`，
返回统一是 `{ok, data, error}`，**失败不 reject**）。

| action | 入参 | 返回（平铺在 `ok:true` 上） | 谁用 |
|---|---|---|---|
| `status` | — | `enabled, lead_min, lead_options, quota, max_quota, template_id, page, ready, ready_reason, field_map, field_types, field_preview, field_preview_text, date_style, date_style_learned, disabled_reason` | 进「我的 → 到期提醒」时读 |
| `ack` | `count`(1..3), `lead_min`(可选) | `enabled, quota, added, capped, max_quota, lead_min` | `wx.requestSubscribeMessage` 成功后上报 |
| `config` | `lead_min`(可选), `enabled`(可选) | `enabled, lead_min, quota, template_id` | 用户改开关 / 改提前量 |
| `test` | `consume_quota`(可选，默认 false) | `sent, quota_consumed, quota, template_id, page, preview, fields, fields_text, fields_text_history, date_style, downgraded, attempts, truncated, warnings` | 「发一条测试提醒」按钮 |
| `scan` | — （`{}` 也算 scan） | `scanned, sent, skipped, failed, quota_refunded, downgraded, errors, warnings, skipped_reasons, details` | **定时器专用**，前端不用调 |

关键约定：

* **`template_id` 必须从 `status` 取，前端不硬编码** —— 换模板只改云函数环境变量。
* `ready === false` 时把 `ready_reason` **原样显示**（它就是给人看的话）。
* 授权成功后 `ack` 的 `count` 就是 `wx.requestSubscribeMessage` 里被接受的模板位数量；
  只传 1..3，服务端会校验，传大了直接拒绝（防刷额度）。
* `test` 默认**不消耗额度**（返回值里 `quota_consumed:false` 说清了）；
  想看真实扣减路径就传 `{"action":"test","consume_quota":true}`。
* `status.field_preview_text` / `test.fields_text` 是**给排查用的**：
  一条形如 `thing2=提交实验报告 | date4=2026年9月28日12:00 | short_thing19=截止`
  的字符串。前端调试面板直接打印它即可，值来自样例/测试任务，**不含用户数据**。

## 9. 已知未验证的部分（照实列）

先分清哪些**已被真机证实**、哪些还只是"按规则写的"：

| 结论 | 状态 |
|---|---|
| `thing` 的上限是**权重**（汉字/全角算 2），20 权重 ≈ 10 个汉字 | ✅ **真机证实**（§2.6 有微信原话 + 复算） |
| 超长会被微信以 47003 整条拒掉（不是只丢那一栏） | ✅ **真机证实** |
| 我们发出的字段与值能从 `reminders.ok:false` 记录里看到 | ✅ **真机证实**（两轮都是靠它定位的） |
| `date` 类**不吃**"年月日 + 时刻"（`2026年10月13日00:09` 被拒） | ✅ **真机证实不可用**（§2.6；代码已自动降级为纯日期并记住） |
| `short_thing19` 的 `截止`（4 权重 ≤ 5） | ⚠️ **未被证伪**（每次都被一起发出去，但整条是因别的字段被拒的） |
| `short_thing`≤5 / `phrase`≤5 / `character_string`≤32 等数值 | ⚠️ 按官方示例与通行规则写的 |
| 下发链路本身（成功路径）、cron、云调用权限、真云集合 | ⚠️ 未验证（见下） |

* **真实下发仍未验证（成功路径）**：真机发过两次，**两次都是失败的** ——
  第一次 47003 因 `thing2` 超长（权重口径已修），第二次 47003 因 `date4` 的形状
  （已实现自动降级 + 记住）。**修好之后的成功路径还没在真机上跑通**。
  下发链路（`cloud.openapi.subscribeMessage.send` 的**成功**返回形状、`lang` 字段是否被接受）
  仍只在**打桩出口**上验证过分支逻辑。
* **自动降级也没有在真机上走通过完整一轮**：逻辑（判定 → 重试 → 记住 → 下次直接用纯日期）
  有单元测试覆盖，但"真机上第二次确实成功"还没发生 —— 下次点测试时请重点看
  `test` 返回里的 `downgraded` / `attempts` / `date_style`。
* **其它类型的数值同样是"按官方示例与通行规则"写的**：`short_thing`≤5 / `phrase`≤5 /
  `character_string`≤32 / `amount`12 / `name`10 … 本地已有"按权重截断 + 本地自检"，
  但**真机才是最终裁判** —— 每类字段的权重上限都可能在真机上被修正一次。
  （`short_thing19` 至今**没被证伪**：它每次都被一起发出去，但整条消息是因别的字段被拒的。）
* **cron 表达式未在控制台验证**：`0 */5 * * * * *` 的 7 位格式按官方文档写，
  但"控制台里确实显示下一次触发时间"这一步要在你部署后自己看一眼（第 3 步）。
* **云调用权限 `permissions.openapi` 未验证**：`config.json` 按官方示例写，
  部署后是否真的免鉴权调通，要看云函数日志里有没有权限类报错。
* **微信错误码分支是按官方语义写的**：`43101` / `47003` / `40001` / `42001` 的
  "含义 → 处理"映射用的是文档与通行经验。`47003` 这一次**被真机触发过**（形状已确认），
  其余三个码**没用真错误码验过**；`extractErrCode` 对多种形状做了兼容。
* **额度回退（`quota_refunded`）未在真机上验证过"微信侧确实没扣"**：
  逻辑依据是"消息没发出去就不该消耗订阅授权"，单元测试覆盖了分支，
  但微信侧的额度计数只能通过在真机上连续观察确认。
* **`reminders` 集合未在真云上建**：本地用内存假数据库验证；真云上要先建集合 + 设权限。
* **多用户并发扫描未验证**：单轮最多处理 200 个用户、每用户最多 3 条；
  真实用户量下的执行时长（云函数默认超时）没测过。
* **扫描用户列表没有翻页**：`fetchEnabledSettings` 只取一批（默认上限 200 行）。
  自用/小范围够用；用户量超过 200 之后排在后面的用户要等前面的行数降下来才会被扫到。
  真到那个量级应该改成"分批 + 游标"，现在的实现**不做**这件事（见代码里的说明）。
