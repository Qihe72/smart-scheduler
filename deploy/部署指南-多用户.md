# 智能日程管家 · 云服务器多用户部署指南

> 面向：一个会用命令行、但没部署过网站的学生。
> 目标：把 `smart-scheduler` 挂到自己的域名上，**你和同学各自有独立的日程**，
> 手机上「添加到主屏幕」后像 App 一样点开就用。
>
> 全程大约 30~60 分钟，其中一半时间在等域名解析和 Docker 下载。
> 文中每个命令都可以直接复制粘贴；**凡是标了 ⚠️ 的地方都踩过坑，别跳过**。

## 第 0 步：先想清楚三件事（不写代码，但最重要）

### 1）你的数据到底存在哪里？

**存在服务器上，存在一个 SQLite 单文件里：容器内的 `/app/data/app.db`。**

- 这个文件在 Docker 的**具名卷 `scheduler-data`** 里（`docker-compose.yml` 里的
  `scheduler-data:/app/data` 这一行），不是在你电脑上，也不在代码仓库里。
- 好处：容器删了、镜像重建了，数据都还在。
- 代价：**`docker compose down -v` 会连卷一起删，数据瞬间清零。**
  这就是为什么下面专门有一节备份。
- 因为数据在服务器上，所以这是一套**多用户**应用：每个浏览器第一次访问会拿到一个
  自己的「空间码」，任务和设置按空间码隔离存储（代码在 `storage.py`）。

一句话：**服务器 = 唯一的数据源，备份 = 你唯一的后悔药。**

### 2）为什么不能用免费的 Streamlit Community Cloud？

因为它的**文件系统会重置**。

Streamlit Cloud（以及 Vercel、Cloudflare Pages 这类"无服务器"托管）跑你的代码时，
容器是随时创建、随时销毁的；重启、休眠、重新部署都会让本地文件回到"刚 git clone 下来"
的状态。而这套应用的数据就写在容器自己的文件系统里（`data/app.db`）：

- 你的同学今天录的作业，明天可能整份消失；
- 服务器一重启，所有人的空间码和日程一起归零；
- 更糟的是**你以为它在存，其实它在丢** —— 这种"静默丢数据"比直接报错难查得多。

Streamlit Cloud 适合"跑个 demo 给别人看"，不适合"存别人真实日程"。
所以这里的方案是：**自己的小服务器 + Docker + 自动 HTTPS**，数据落在服务器的持久卷上。

> 顺带一提：如果哪天你真想用无服务器托管，正确做法是把 `storage.py` 里的 SQLite
> 换成 Postgres/云数据库 —— 那是另一件事，不是改几行配置能完成的。

### 3）「空间码」意味着什么：知道即拥有，没有密码

这套多用户设计**故意不做注册/密码**：第一次打开自动分配一个随机空间码（约 11 个字符），
写进网址的 `?u=xxxx` 里，手机装到桌面后就不用再输。

必须诚实地说清它的性质：

| 特性 | 说明 |
|---|---|
| 没有密码 | 空间码就是唯一的"钥匙"，**知道码的人 = 拥有那份日程**（能看、能改、能删） |
| 不可找回 | 没有邮箱验证、没有"忘记密码"。码丢了 = 那份日程打不开了 |
| 不要外传 | 别把带 `?u=` 的完整链接发到群里 —— 那等于把日程的钥匙发出去 |
| 别放敏感信息 | 学号、身份证、成绩、密码这类东西不要写进去 |
| 有出口 | 界面上有「导出我的数据」和「删除我的空间」，随时能走 |

对"我和几个同学存作业 DDL"这个场景，这个取舍是合理的（不用注册，门槛极低）。
对"要给全班用、还要防止互相看到"，**这个方案不够** —— 见
[第 9 步](#第-9-步资源与安全诚实版)最后一节，那时要做的是把 `storage.py` 的身份层换成真正的登录。

## 第 1 步：准备

### 1.1 一台服务器

| 项目 | 建议 | 说明 |
|---|---|---|
| 配置 | **1 核 2G 内存** 起 | Streamlit 本身吃内存（Python + Pandas），1G 会频繁被杀进程 |
| 系统 | Ubuntu 22.04 / 24.04（Debian 12 也行） | 本指南命令按 Ubuntu 写 |
| 硬盘 | 20G 起 | 应用镜像约 1.5~2G，数据本身很小（几百人也就几十 MB） |
| 地域 | 国内机房或香港/日本轻量 | 国内机房要域名备案；不想备案就选境外 |

学生党常见的便宜选择：阿里云/腾讯云的学生机、Vultr/DigitalOcean 最低档、
各类"轻量应用服务器"。**1 核 2G 大概够 10~30 个同学用**（依据见第 9 步）。

### 1.2 一个域名 + A 记录

1. 在域名商（阿里云/腾讯云/Namesilo/Cloudflare…）买一个便宜域名（`.top`/`.xyz` 一年十几块）。
2. 进 DNS 解析页面，加一条 **A 记录**：

   | 记录类型 | 主机记录 | 记录值 | TTL |
   |---|---|---|---|
   | A | `schedule`（或 `@` 表示直接用主域名） | **你服务器的公网 IP** | 600 |

   配好后，`schedule.你的域名.com` 就指向你的服务器了。
3. 检查解析是否生效（在你自己的电脑上执行，**不是**服务器上）：

   ```bash
   ping schedule.你的域名.com      # 或者用 nslookup / dig
   ```

   ⚠️ **必须看到你服务器的 IP 才能继续**。Caddy 申请证书时会去访问这个域名，
   解析没生效就一定失败。DNS 一般 1~10 分钟生效，慢的半小时。

   > 国内机房提醒：域名解析到大陆服务器、并且要开 80/443 提供网站服务，
   > 按规定需要 ICP 备案。用境外服务器或者买来先玩自己的局域网则不需要。

### 1.3 装 Docker

SSH 登进服务器（`ssh root@你的服务器IP`），然后：

```bash
# 官方一键脚本（最省事，适合个人服务器）
curl -fsSL https://get.docker.com | sh

# 确认装好了：两条命令都要有版本号输出
docker --version
docker compose version        # 注意是 "docker compose"（空格），不是 "docker-compose"
```

> ⚠️ 一定要有 **docker compose** 子命令（Compose V2，随 Docker 一起装）。
> 如果 `docker compose version` 报错、只有 `docker-compose`，说明装的是老的 V1，
> 下面的命令把 `docker compose` 换成 `docker-compose` 也能用。

### 1.4 放行 80 和 443

**这一步最容易漏，漏了就是"证书申请失败"。** 要在两个地方都放行：

1. **云厂商的安全组 / 防火墙**：在控制台找到"安全组"或"防火墙"，加规则
   放行入方向 `TCP 80` 和 `TCP 443`（来源 `0.0.0.0/0`）。
2. **服务器自己的防火墙**（如果开了 ufw/firewalld）：

   ```bash
   sudo ufw allow 80/tcp
   sudo ufw allow 443/tcp
   sudo ufw reload
   sudo ufw status          # 确认 80/443 是 ALLOW
   ```

⚠️ 不要放行 8501！应用端口只在 Docker 内部用，由 Caddy 转发，
对外暴露 8501 等于绕过了 HTTPS。

顺便确认 80/443 没被别的程序占着（新服务器一般没事）：

```bash
sudo ss -lntp | grep -E ':80|:443'      # 没有输出最好；有输出就先停掉那个服务
```

## 第 2 步：把代码放上服务器

### 2.1 ⚠️ 服务器不该拿到机主的私人日程

这是整份指南里最需要小心的一步。项目里有三类东西**绝对不要上传**：

| 不该上传的东西 | 里面是什么 | 为什么 |
|---|---|---|
| `data/schedules.json`、`data/settings.json` | 机主本机自用时的真实课表、作业、学期设置 | 那是私人日程，服务器上不需要它 —— 多用户版用的是 `data/app.db`，由容器启动时自己建 |
| `.env` | `DEEPSEEK_API_KEY` | 密钥只在部署机上放一份；`.env.example` 可以传，`.env` 不行 |
| `.memsearch/` | 本机的 AI 记忆/检索日记（含开发过程对话） | 和运行无关，纯属隐私 |

好消息：这三类**都已经写在项目 `.gitignore` 里**（`.env`、`data/schedules.json`、
`data/settings.json`、`.memsearch/`），而且 `.dockerignore` 又把 `data/` 和 `.env`
排除了一次 —— 也就是说镜像里永远是"空数据"。

**但"被 gitignore"只在用 git 的时候有效**。如果你是 `scp -r` 整个文件夹、或者打 zip
上传，这两个清单都不会帮你挡住。所以上传前先自己核对一遍。

#### 推荐做法：用 git（最安全）

```bash
# 在你自己的电脑上，项目根目录
cd C:\Users\qihe\Desktop\日程安排\smart-scheduler
git status --ignored --short | Select-String "data/|\.env|memsearch"   # PowerShell：确认这些是被忽略的
git add -A
git commit -m "多用户版"
git push                     # 推到 GitHub/Gitee 的私有仓库

# 然后在服务器上
sudo mkdir -p /opt/smart-scheduler && cd /opt/smart-scheduler
git clone <你的私有仓库地址> .
```

#### 或者：用 scp 直传（要手动排除）

```bash
# ⚠️ Windows 上建议用 tar 打包再传，能顺便排除文件
# 在项目根目录的上一级执行：
tar --exclude='./data/*.json' --exclude='./data/app.db' --exclude='./.env' \
    --exclude='./.memsearch' --exclude='./__pycache__' --exclude='./.git' \
    -czf smart-scheduler.tgz -C 日程安排 smart-scheduler

scp smart-scheduler.tgz root@你的服务器IP:/tmp/
# 服务器上：
sudo mkdir -p /opt/smart-scheduler && sudo tar -xzf /tmp/smart-scheduler.tgz -C /opt/smart-scheduler --strip-components=1
```

> 上传完在服务器上`ls -a`看一眼：**不该出现 `.env`、`.memsearch/`**；
> `data/` 目录可以存在（容器需要它），但里面**不该有 schedules.json**。

### 2.2 最终目录结构

上传完 + 把 `deploy/` 放进去之后，服务器上应该是这样：

```
/opt/smart-scheduler/                <- 项目根（也是镜像 build 的 context）
├── Dockerfile
├── requirements.txt
├── main.py  storage.py  config.py  ui_components.py  ...
└── deploy/                          <- 部署产物都在这
    ├── docker-compose.yml
    ├── Caddyfile
    ├── index.html                    <- 静态启动页（带 manifest）
    ├── manifest.webmanifest
    ├── sw.js
    ├── icons/icon-192.png
    ├── icons/icon-512.png
    ├── make_icons.py                 <- 图标生成脚本（服务器上不需要跑）
    ├── backup.sh
    ├── .env                          <- 第 3 步创建，不进 git
    └── .env.example
```

**为什么要有 `index.html` 这个静态启动页？**
Streamlit 不允许往 HTML 的 `<head>` 里注入内容，而手机「添加到主屏幕」要求页面里有
`<link rel="manifest">`。所以方案是：Caddy 自己发一个带 manifest 的静态启动页，
Streamlit 退到子路径 **`/app`** 上（应用侧用 `--server.baseUrlPath=app`），
启动页用 iframe 把它整屏嵌进去。⚠️ 这两个 `/app` 必须一致，改一个就得改另一个。

## 第 3 步：改两个文件（域名、邮箱、Key）

### 3.1 `deploy/Caddyfile`：改域名和邮箱

```bash
cd /opt/smart-scheduler/deploy
nano Caddyfile
```

找到最上面这两行，改成你自己的：

```caddyfile
schedule.你的域名.com {        # ← 改成你的域名（只写域名，不要带 https:// 和斜杠）
        email you@example.com  # ← 改成你的真实邮箱（证书出问题时 Let's Encrypt 用它通知你）
```

保存退出：`Ctrl+O` 回车，`Ctrl+X`。

要点：

- 站点地址**只能写一个域名**，Safari 的「添加到主屏幕」和 Service Worker 都要求同源。
- 邮箱随便填也能签下证书，但证书快过期/域名有异常时你会收不到通知，**建议填真的**。
- `reverse_proxy app:8501` 里的 `app` 是 compose 里的服务名，不用改。

### 3.2 `deploy/.env`：API Key（可选）

```bash
cd /opt/smart-scheduler/deploy
cp .env.example .env
nano .env
```

填成：

```
DEEPSEEK_API_KEY=sk-你的真实key
```

- **可选**：不填也能用全部非 AI 功能（手动录入、课表导入、周视图、本周空档、
  进度追踪、导出/删除空间）。只有"一句话自然语言录入"会提示未配置 Key。
- `.env` 已在 `.gitignore` 里，不会被提交；权限收紧一点更稳妥：

  ```bash
  chmod 600 .env
  ```

- ⚠️ 千万别把 Key 直接写进 `docker-compose.yml` —— 那个文件是要提交到仓库的。

## 第 4 步：起服务

```bash
cd /opt/smart-scheduler

# 第一次要 build 镜像（下载 python:3.12-slim + 装依赖），慢的话 5~10 分钟
docker compose -f deploy/docker-compose.yml up -d --build

# 看日志（第一次重点看 caddy：证书就是这会儿申请的）
docker compose -f deploy/docker-compose.yml logs -f
# 按 Ctrl+C 退出看日志（不会停服务）
```

Caddy 日志里出现下面这类字样，说明证书签好了：

```
certificate obtained successfully    identifier=schedule.你的域名.com
```

> **小技巧**：在 `deploy/` 目录里执行就可以省掉 `-f`：
> `cd /opt/smart-scheduler/deploy && docker compose up -d --build`。
> 因为 `-f` 指定的文件所在目录会成为相对路径的基准（`./Caddyfile`、`build: ..`
> 都相对它解析），两种写法的效果完全一样。
>
> 常用命令（下面都省略 `-f deploy/docker-compose.yml`，请按需补上）：
> `docker compose ps` / `logs -f app` / `restart caddy` / `down`（**不要加 `-v`**）。

## 第 5 步：三步验证

按顺序来，哪一步不对就停下查[第 8 步](#第-8-步常见问题照着这个表查)的问题表。

### ① 容器状态

```bash
docker compose -f deploy/docker-compose.yml ps
```

期望：`app` 和 `caddy` 两个服务都是 **Up**；等半分钟再看，`app` 应该显示
**`(healthy)`** —— 那是 Dockerfile 里那个健康检查在打 `/_stcore/health`。

```
NAME       SERVICE   STATUS
ss-app     app       Up 2 minutes (healthy)
ss-caddy   caddy     Up 2 minutes
```

如果 `app` 一直是 `(health: starting)` 或 `(unhealthy)`：

```bash
docker compose -f deploy/docker-compose.yml logs --tail=100 app
```

### ② 应用健康端点（证明反代 + 子路径都通了）

```bash
curl https://schedule.你的域名.com/app/_stcore/health
```

期望输出就一个词：

```
ok
```

⚠️ 这里的 `/app` 就是 `--server.baseUrlPath=app` 带来的：应用挂在子路径下，
它的健康端点也跟着变成 `/app/_stcore/health`。如果你 curl 根路径的
`/_stcore/health` 得到 404，那是**正常的**。

### ③ 首页与 manifest

```bash
curl -I https://schedule.你的域名.com/
```

期望：`HTTP/2 200`，且 `content-type: text/html...`。

```bash
curl -s https://schedule.你的域名.com/manifest.webmanifest | head -3
```

期望：能直接看到 JSON（第一行是 `{`，接着是 `"name": "智能日程管家",`）。
如果返回的是 HTML 或 404，说明 Caddyfile 里静态那条 `handle` 没生效。

再顺手确认一下访问时会不会自动跳到 https：

```bash
curl -I http://schedule.你的域名.com/       # 期望 308，Location 指向 https://...
```

**最后在电脑浏览器里打开一次** `https://schedule.你的域名.com/`：
应该先看到「正在加载…（第一次会慢一点）」，然后整屏出现应用。
地址栏里应用那一层是 iframe（`/app`）。

## 第 6 步：手机上「添加到主屏幕」

不需要 Mac，也不需要开发者账号。**iOS 必须用 Safari**（Chrome/微信内置浏览器
不行，因为 iOS 上只有 Safari 能装 Web App）；Android 用 Chrome。

**iOS（Safari）**

1. 用 Safari 打开 `https://schedule.你的域名.com/`；
2. 点底部的「分享」按钮（方框 + 向上箭头）；
3. 往下滑，选「**添加到主屏幕**」→ 右上角「添加」；
4. 桌面出现「日程管家」图标（蓝色圆角方块 + 白色日历），点开就是全屏，没有地址栏。

**Android（Chrome）**

1. 用 Chrome 打开同一个网址；
2. 右上角「⋮」→「**安装应用**」/「添加到主屏幕」（有的版本会直接弹提示）；
3. 确认后桌面出现图标，点开是全屏。

装好之后：

- **每个人自己装自己的一份**。第一次访问时服务器已经给你分配了空间码、写在网址里，
  装到桌面时这个地址被一起保存下来了，所以之后点开就是你自己的日程，不用输码。
- 换手机、清了浏览器数据、或者想在电脑上用同一个空间：打开主页的
  「🔑 我的空间」面板，把**空间码**抄过去，在新设备的「输码进入」里填上即可。
- ⚠️ 空间码别发到群里 —— 知道码的人就能看和改你的日程（见第 0 步第 3 条）。

## 第 7 步：备份与恢复

### 7.1 手动备份一次（先跑通，再放定时任务）

```bash
cd /opt/smart-scheduler
bash deploy/backup.sh /mnt/backup 30
```

参数：`备份到哪个目录` 和 `保留多少份`（默认 `./backups` 和 14 份）。
脚本做的事：

1. 用 `docker compose exec app python -c "... sqlite3 ... src.backup(dst)"` 在容器内
   调 SQLite 的**在线备份 API** —— 不停服务、多人正在用也能拿到一致性快照
   （直接 `cp` 数据库文件是不安全的：开了 WAL，可能拷到半个事务）；
2. `docker compose cp` 把快照拷到宿主机；
3. 删掉容器里的临时文件；
4. 按份数轮转旧备份。

跑完会打印 `✅ 备份完成：/mnt/backup/app-20260925-033000.db` 和当前备份列表。

### 7.2 定时备份（每天凌晨 3:30）

```bash
crontab -e
```

整行粘进去（注意路径按你的实际情况改）：

```cron
30 3 * * * cd /opt/smart-scheduler && /usr/bin/bash deploy/backup.sh /mnt/backup 30 >> /var/log/ss-backup.log 2>&1
```

再保险一点：每周日 4 点额外备一份到别的目录/网盘挂载点（3-2-1 原则：至少两份介质）。

```bash
tail -f /var/log/ss-backup.log      # 第二天来看看有没有跑成功
```

> 至少定期把某一份拖到你的电脑或网盘上。

## 第 8 步：常见问题（照着这个表查）

| 现象 | 最可能的原因 | 怎么修 |
|---|---|---|
| Caddy 日志里 `challenge failed` / `no such host` / 证书申请失败 | ① 域名 A 记录没生效；② 云安全组没放行 80；③ 域名拼错了 | `ping 你的域名` 确认解析到服务器 IP；控制台放行 80/443；`sudo ss -lntp \| grep :80` 看 80 是否被别的程序占用 |
| 浏览器提示 `ERR_CONNECTION_REFUSED` / 打不开 https | Caddy 没起来，或 443 没放行 | `docker compose ps` 看 caddy 是否 Up；`docker compose logs caddy` 看报错；确认安全组放行 443 |
| **白屏**：启动页出来了，但里面一直是空白/转圈 → 最后提示"加载好像卡住了" | ① Caddy 到 app 的 **WebSocket** 没通；② **`baseUrlPath` 不一致**（应用挂在 `/app` 但 Caddy 没转发 `/app`，或反之） | ① 检查 Caddyfile 有 `handle /app* { reverse_proxy app:8501 }`（Caddy 默认支持 WebSocket 升级，不需要额外配置）；② 确认 `command` 里的 `--server.baseUrlPath=app` 与 Caddyfile 里的 `/app*`、index.html 里的 `iframe src="/app"` **三处完全一致**；③ `docker compose logs -f app` 看有没有 404/重定向循环 |
| 白屏但浏览器控制台有 `404 ... /static/...` 之类的报错 | 静态资源路径不对，通常是子路径没配好 | 同上，三处 `/app` 必须一致；改完 `docker compose restart app caddy` |
| 「两个人看到同一份日程」 | 他们打开的是**同一个空间码**（比如都用了你发出去的那条带 `?u=` 的链接，或者同一台设备同一浏览器） | 让每个人自己打开主页 `https://域名/` 领新空间码；在「🔑 我的空间」里核对码是否不同；清掉地址里别人的 `?u=` |
| 自己突然看到"别人的"日程 | 上一条的另一种表现：浏览器记住了旧的空间码 | 打开 `https://域名/`（不带任何参数）重新领一个；或用「输码进入」填回自己的码 |
| 改完 Caddyfile 没生效 | Caddy 不会热加载挂载的 Caddyfile | `docker compose restart caddy` |
| 手机装不上「添加到主屏幕」/ 装出来是浏览器快捷方式 | 用了微信/Chrome 打开的 iOS 页面；或没走 https | iOS 必须 Safari；必须是 `https://`（http 下浏览器不允许装 Service Worker）；清掉旧图标重装一次 |
| 装了桌面图标，打开还是旧界面 | 静态壳被 Service Worker 缓存了 | 正常最多等几分钟（壳只缓存 5 分钟）；急就改 `sw.js` 里的 `ss-shell-v1` → `v2`，重启 caddy 后重开一次 |
| `app` 一直 unhealthy | 应用启动崩了（缺依赖/语法错误/内存不足） | `docker compose logs --tail=200 app` 看 traceback；`free -h` 看内存是不是被 OOM 杀了 |
| 服务器重启后一切正常但数据没了 | ⚠️ 有人执行过 **`docker compose down -v`** 或 `docker volume rm`，把 `scheduler-data` 卷删了 | 用第 7 步的备份恢复。⚠️ **别用 `down -v`**，只想停服务用 `docker compose down`（不带 `-v`）或 `stop` |
| `docker compose down` 会不会丢数据？ | 不会 | 不带 `-v` 的 `down` 只删容器和网络，**具名卷保留**。容器下次 `up` 时数据还在 |

> **关于 `-v` 的完整解释**（值得记一辈子）：
> `docker compose down` = 删容器；`docker compose down -v` = 删容器 **+ 删数据卷**。
> 那个 `-v` 是 `--volumes` 的缩写，它删掉的就是 `scheduler-data` ——
> 也就是所有人的日程，**不可恢复**。想彻底重装环境时，先备份再考虑它。

## 第 9 步：资源与安全（诚实版）

### 9.1 一台 1核2G 大概能撑多少人？

**大约 10~30 人日常使用。** 说明一下这个数字是怎么来的、什么时候会不够：

- Streamlit 是"一个有状态的长连接 + 每次交互重跑一遍脚本"的模型，**每个活跃
  浏览器会话都占内存**。空载时 `app` 容器大约 200~350MB；每个活跃会话再加
  几十 MB（取决于页面上的数据量）。
- 2G 内存里还要留 ~200MB 给 Caddy 和系统。所以**同时在线** 10~20 人是舒适区，
  30 人是上限附近。
- CPU 不是瓶颈（1 核够用），内存才是。人一多最先出现的症状是：
  页面变慢 → 连接中断 → 容器被杀（`docker inspect` 里能看到 `OOMKilled`）。
- 想扩容最有效的三件事：
  1. **加内存**（2G → 4G，最直接）；
  2. 在 `docker-compose.yml` 里给 app 加内存上限，免得它吃掉整台机器：
     ```yaml
     deploy:
       resources:
         limits:
           memory: 1500m
     ```
  3. 升级到换 Postgres 存储（SQLite 单写者模型在几十人高频写入时会有排队）。

### 9.2 空间码就是全部的安全性

请把这句话当作设计事实，而不是警告文案：

- **空间码泄露 = 数据泄露。** 拿到 `?u=xxxx` 的人可以看、改、删那份日程，
  没有任何二次验证。
- 码本身是随机的（`secrets.token_urlsafe(8)`，约 11 个字符，猜中概率可以忽略），
  所以风险不在"被猜"，而在"**被看到/被转发**"：截图、群里贴链接、共用电脑的
  浏览器历史。所以项目里才写了"别放敏感信息"。
- 已经做的缓解：数据按码隔离（互相看不见）、有「导出我的数据」和「删除我的空间」
  两个出口、SQLite 开了 WAL 与 `busy_timeout` 保证多人在线时不锁死。
- **没做的**：没有密码、没有找回、没有审计日志、没有限流。所以别把它当成
  "能存成绩单的系统"。

运维侧还应该做的三件小事：

1. **别对外暴露 8501**：只让 Caddy 转发（本 compose 里 `app` 没有 `ports`，
   就是对的做法）；顺手确认安全组没放行 8501。
2. **`DEEPSEEK_API_KEY` 留在服务器上的 `.env` 里**，`chmod 600`，别提交，
   别贴在群里，并在 DeepSeek 后台设个额度上限（防跑飞）。
3. **定期备份 + 偶尔真恢复一次**。没验证过能恢复的备份，等于没有备份。

### 9.3 想要"真账号"该怎么办

现在的身份层在 **`storage.py`**：它把"当前请求属于哪个空间"简化成了一个
URL 参数（`?u=<空间码>`），`SS_MULTIUSER=1` 时由 `main.py` 在每次页面重跑时
设置一次。要变成真正的登录（用户名 + 密码 / 邮箱验证码 / 学校统一认证），
需要换掉的就是这一层，大致是：

1. 加一张用户表（用户名、密码哈希 —— 用 `hashlib.scrypt` 或 `bcrypt`，
   **绝对不要明文存密码**）和会话表；
2. 登录成功后把身份写进 Streamlit 的 `st.session_state`（而不是 URL 参数），
   未登录时只显示登录页；
3. `storage.py` 里所有按 `space` 过滤的查询改成按 `user_id` 过滤
   （现在的"空间"概念可以自然升级成"账号"，数据表结构基本不用动）；
4. 再顺手补上：会话过期、登录限流、修改/重置密码的流程。

这是个明确的、有边界的改造（主要集中在 `storage.py` + 新增一个 `auth.py`
+ 登录界面），但它**不是**这份部署指南的范围 —— 在那之前，请按第 0 步第 3 条
的定性使用：**小范围、熟人、不放敏感信息。**
